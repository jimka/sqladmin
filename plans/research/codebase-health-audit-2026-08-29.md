# Codebase health audit — 2026-08-29 (SQLAdmin)

Companion to the same-day whole-codebase health audit of the underlying `typescript-ui` library (`duplicated code, overlapping functionality, dead/unused code`), rescoped to the SQLAdmin app itself. This is the app's first such audit — the full codebase, not a delta since a prior pass.

**Scope:** `frontend/src` (~23,000 lines, 136 files) and `backend/app` (~10,050 lines, 45 files).

**Method:** 7 independent fresh-context reviewers (the project's `audit` skill's standard reviewer, one per subsystem slice), each reading the governing docs it could find (`frontend/COMPONENT_CONVENTIONS.md`, `backend/README.md`, `LIBRARY_NOTES.md`, the global `CODE_CONVENTIONS.md` — this repo has no `CLAUDE.md`/`ARCHITECTURE.md` at its root), then auditing its slice against BLOCKING/ADVISORY criteria, focused on duplication/overlap/dead-code but free to report real bugs found incidentally. No reviewer saw another's output — where two independently flagged the same code, it's called out below as corroboration. One reviewer (backend operations) verified a suspected crash live against the running `sqladmin-db` container, in a rolled-back transaction.

**Totals: 64 BLOCKING findings, ~85 ADVISORY findings**, across:

| Subsystem | Blocking | Advisory |
|---|---|---|
| DDL forms & dialogs | 8 | 12 |
| Diagrams & graph data layer | 10 | 10 |
| Info panels & query workspace | 8 | 15 |
| Data layer & navigator/roles/properties | 7 | 12 |
| Shell & app controller wiring | 10 | 10 |
| Backend operations (CQRS handlers) | 11 | 11 |
| Backend core infra & SQL layer | 10 | 15 |

This document is a survey, not yet acted on — see **Recommendation** at the end.

## Priority 1 — Real correctness bugs, leaks, and security-relevant gaps

### Frontend

**1. Removed DDL-form grid rows are never disposed — a real leak in all four multi-row forms.** `CreateTableForm`, `EnumTypeForm`, `CompositeTypeForm`, and `FunctionForm` each remove a row via `this._gridPanel.removeComponent(input)` (`frontend/src/dock/CreateTableForm.ts:123-125`, `EnumTypeForm.ts:104-106`, `CompositeTypeForm.ts:120-122`, `FunctionForm.ts:164-166`). Verified against the shipped library bundle: `removeComponent` only detaches and unwires — it does not dispose. Every removed row's inputs and its `removeButton` (with a live `"action"` listener) survive detached until GC, and the dialog's own teardown can't reach them since it only cascades into currently-attached children. The app already applies the correct fix one file over for its error banners (`SqlPreviewDialog.ts:212-225`, `ImportRowsDialog.ts:174-188`); these four forms just don't.

**2. A legend-dispose fix landed in three of four sibling diagram panels — `RootedRelationGraphPanel` still leaks.** `RootedRelationGraphPanel.rebuildLegend` clears the legend with `removeAllComponents()` (`frontend/src/dock/RootedRelationGraphPanel.ts:98`), which only detaches rows. The commit that fixed this ("Dispose legend rows on rebuild instead of just detaching them") touched `diagramShell.ts:127`, `RelationDiagramPanel.ts:187`, and `DatabaseDiagramPanel.ts:199` — and never `RootedRelationGraphPanel.ts`. Every Direction/Depth change on a rooted dependency or inheritance graph still orphans one `Checkbox`+`Text` pair per node in the base graph, live today.

**3. Four of five flat diagram builders skip the fix for staggered node columns.** `uniformNodeWidth.ts:51-59`'s own header explains the problem it solves — label-sized nodes stagger a layer by up to 85px so "the columns stop reading as columns" — but only `buildSchemaDiagram.ts:123` calls it. `buildDatabaseDiagram.ts` (the Tables-mode whole-database graph, the largest diagram in the app), `buildRelationGraph.ts`, `buildRoleGrantsDiagram.ts`, and `buildRoleMembershipDiagram.ts` all emit unwidthed nodes, so all four have the staggering the helper exists to prevent, live today.

**4. The role-membership graph shows a checkbox that can never do anything.** `SqlAdminController.ts:3234` opens the role-membership DAG through `RelationDiagramPanel`, which unconditionally adds a "Highlight FKs without a covering index" checkbox and wires FK-coverage styling and FK-edge tooltips (`RelationDiagramPanel.ts:101-107,141,160-161`). A membership graph has no foreign keys — the control is permanently inert. The panel's own JSDoc acknowledges the reuse but not this consequence.

**5. Returning from Tables mode to Overview mode leaves the diagram at the wrong zoom.** `DiagramShell.settleViewport` decides `zoomToFit()` vs `focusNode(root)` from `this.rootId` alone (`diagramShell.ts:452-465`), but `DatabaseDiagramPanel` has a third state — Overview, where "the drawn graph is the schema overview, not the rooted table graph at all" (`DatabaseDiagramPanel.ts:14-18`) — that the shell doesn't know about. After choosing a table root in Tables mode and switching back to Overview, `settleViewport` calls `focusNode("&lt;schema&gt;.&lt;table&gt;")` against the schema-overview graph; the library falls through to a plain re-centre with no fit, leaving the overview at whatever zoom the table graph was last at.

**6. Dropping a constraint or index can permanently close the Structure tab.** `SqlAdminController.refreshStructure` (`SqlAdminController.ts:1756-1765`) — called by the constraint/index add/drop launchers — removes the Structure panel and only reopens it `if (node)`, where `node` comes from the panel registry. A Structure tab opened via a deep link (`shell/appRouter.ts:181`) or via `openReferencedStructure` when a reveal finds nothing stores `node: null`. In that case, adding or dropping a constraint or index **closes the tab and never reopens it** — contradicting the code's own comment that this "should not happen in practice." `openStructure` already registers a correct in-place `refresh` closure (`SqlAdminController.ts:939-950`) that the DDL launchers should be dispatching to instead.

**7. `shortcutsDialog` reintroduces a nested-scrollbar bug `changelogDialog` already diagnosed and removed.** `changelogDialog.ts:11-19` explains at length that `Dialog`'s own content container already scrolls, so a second `autoScroll` nests one scroll region inside another — and removes it. `shortcutsDialog.ts:36` still sets `autoScroll: "y"` (with a comment arguing to keep it), so the Shortcuts dialog gets a double scrollbar whenever the legend overflows the viewport — the exact defect its sibling dialog already fixed.

**8. ~30 of 32 frontend API URL builders don't percent-encode path segments.** Only `tableExportUrl` (`frontend/src/data/api.ts:305-310`) and `getRoleDetail` (`api.ts:529`) escape the database/schema/relation/role names they interpolate. Every other builder — all nine `list*`/`get*` introspection calls, both import routes, all ~25 `preview*`/`executeDdl` DDL routes, and the row-CRUD proxy URL (`data/stores.ts:25`) — interpolates raw. Postgres identifiers may legally contain `/`, `?`, `#`, `%`, and spaces; any of those in a real object name produces a wrong or truncated request (`#` truncates client-side before the request is even sent). `frontend/tests/data/api.test.ts:182` pins the requirement for the one function that has it.

**9. "Clear SQLAdmin data" silently destroys saved connection presets, with no warning.** `clearAppKeys()` (`shell/localStorageWindow.ts:153-164`, invoked at `:268-272`) removes every `sqladmin.*` key, including `sqladmin.presets` (`data/presetStore.ts:15`) — irrecoverable saved-server data. The module's own header, which enumerates what gets cleared, omits presets entirely (`:19-24`, `:41-44`), and unlike sign-out (`SqlAdminShell.ts:447-450`, which uses `Dialog.confirm`), the clear action asks nothing.

**10. `LoadSignal.arm()` does the opposite of its documented behaviour — a real race.** `data/loadSignal.ts:24-26` claims a re-`arm()` mid-load "extends the existing wait." It's a no-op while armed instead, so the *first* load's `settle()` resolves the shared promise and the wait is **truncated** to whichever load finishes first (pinned by `frontend/tests/data/loadSignal.test.ts:52-63`) — the exact race the signal exists to prevent. A reveal awaiting `whenLoaded()` across two overlapping `refresh()` calls can search a half-populated tree.

### Backend

**11. `ListInheritanceQuery` 500s on any schema with a partitioned index — verified live.** `list_inheritance.py:29-40` selects `relkind` from `pg_inherits` with no relkind filter, then `get_result()` does an unguarded lookup into `_RELKIND_KIND` (`list_inheritance.py:18`), which only covers `r/p/f/v/m`. Since Postgres 11, `pg_inherits` also records partitioned-index→index-partition edges (`parent_kind='I', child_kind='i'`), confirmed against a live PG 16 container. `KeyError` isn't a `DomainError` or `asyncpg.PostgresError`, so neither exception handler in `main.py:167-185` catches it — `GET /{schema}/inheritance` 500s. The sibling `ListDependenciesQuery` avoids this because it *does* filter relkinds in SQL (`list_dependencies.py:44-45`) — the guard exists, just not in both copies (see Priority 2 #7). Latent today only because the seed DB has zero `pg_inherits` rows.

**12. The same missed-fix pattern as #11 affects `table_structure.py`'s index query.** `graph.py:208-212` documents fixing an index-listing join predicate from `n.nspname = $1` to `n.nspname = i.schemaname`; `table_structure.py:57` and `:122` (`ListIndexesQuery` and `IndexDetailQuery`, both independent copies of the same query) never received that fix. Worth confirming directly whether the old predicate is still wrong there before deciding this is cosmetic.

**13. Two boolean env-var parsers with diverging semantics — `ALLOW_USER_PRESETS=off` silently stays on.** `config.py:30` defines `_FALSEY = {"0","false","no"}` (used only by `allow_user_presets()`); `config.py:36-37` defines a separate `_TRUE_VALUES`/`_FALSE_VALUES` pair (adding `"on"`/`"off"`) used by `parse_bool()`, which backs `enable_docs()` and `auth.py`'s `cookie_secure`. So `SQLADMIN_ENABLE_DOCS=off` and `SQLADMIN_COOKIE_SECURE=off` are false, but `ALLOW_USER_PRESETS=off` is **true** — the flag stays on. `tests/test_config.py:88-92` locks this in by asserting `"anything"` → `True`. Both the root `README.md:210` ("set falsy") and `backend/README.md:33-34` ("`false`/`0`/`no`") tell an operator to use a value that has no effect on this one flag.

**14. Login's error handling is an allowlist with no catch-all — some auth failures bypass the rate limiter and leak raw driver text.** `auth.py:249-259` enumerates five caught exception types and only records a login failure for `DomainError` (`:260-262`). Confirmed against installed asyncpg: `InsufficientPrivilegeError` (no `CONNECT` grant), `TooManyConnectionsError`, `ClientCannotConnectError`, and `ProtocolViolationError` are all `PostgresError` subclasses outside those tuples, so they fall through to the generic pg-error handler and return **400 with `str(exc)`** — Postgres's own message verbatim, and `record_login_failure` never runs. A permission-denied login costs an attacker nothing against the 10-attempt lockout, and the `login` docstring's claim of "a generic detail that never echoes... raw driver text" is false for this path.

**15. Route registration order makes a role named `schemas` or `graph` unreachable.** `GET /api/{connection_id}/{database}/schemas` and `.../graph` are registered before `GET /api/{connection_id}/roles/{role}`. Resolved against the real app: `/api/default/roles/schemas` matches the schemas route with `database="roles"` instead of the role-detail route with `role="schemas"`. Postgres permits role names like `schemas`/`graph`; the role-detail page for such a role silently shows the wrong content.

**16. `Content-Disposition` is built from unsanitized identifiers.** `main.py:1609` interpolates `{schema}`/`{table}` (URL path segments, percent-decoded by FastAPI) straight into the export filename header. Postgres permits `"` in an identifier, which breaks the quoting; a CR/LF in the name is rejected downstream as a 500. Low severity (same-session attacker/victim), but unvalidated input in a response header.

**17. The export-format allowlist and the export media-type map can drift apart into a 500.** `operations/export_rows.py:28` (`_VALID_FORMATS`) and `main.py:1554` (`_EXPORT_MEDIA`) independently name the supported formats; the route indexes the second unguarded (`main.py:1593`). Adding a format to one without the other is a `KeyError` after the session/table checks have already passed. Latent, not yet triggered.

## Priority 2 — Structural duplication that should converge

### Frontend — DDL forms

**1. The add/remove-row grid is implemented four times, near-verbatim.** `CreateTableForm`, `EnumTypeForm`, `CompositeTypeForm`, and `FunctionForm` each carry their own row-handle interface, the same `Grid`+"Add X" `Button` construction, and byte-identical `removeRow`/`syncGrid` private methods (`CreateTableForm.ts:62-140`, `EnumTypeForm.ts:49-121`, `CompositeTypeForm.ts:56-139`, `FunctionForm.ts:83-182`). No shared helper exists anywhere in the repo. A `RowGridPanel<TRow>` base taking a per-row cell factory would absorb all four — and would also fix Priority 1 #1 in one place instead of four.

**2. The error banner is implemented three times, verbatim.** `SqlPreviewDialog.ts:82,159-225`, `ImportRowsDialog.ts:77,127-188`, and `QueryPanel.ts:123,637-677` each independently declare the same background color, the same dismiss button, and the same show/hide/dispose-if-detached trio. Each file's comment concedes the copy but justifies it as "just one CSS-var literal" — true of the constant, not of the ~40 surrounding lines, and there are now three copies.

**3. `DropRelationForm` duplicates the shared `ConfirmCascadeForm` it should be using.** `RelationDdlActions.ts:34-50` re-declares the identical summary+CASCADE-checkbox panel, including the same label string, that `ConfirmCascadeForm.ts:15-37` already provides and that every other drop flow uses (schema, sequence, table, constraint, index, function, type). `RelationDdlActions` is the lone holdout.

**4. `readOnlyTable()` is bypassed at three call sites — flagged independently by two reviewers.** `columnsGrid.ts:122-124` exists to own the `Table(store, { columns: [], autoSizeColumns: true, rowReadOnly: () => true })` spec, and `StructurePanel.ts:594,611` use it — but `ImportRowsDialog.ts:107`, `RoleGrantsPanel.ts:50`, and `QueryResultView.ts:97` all re-type the identical expression instead.

**5. DDL dialog launchers are wired two incompatible ways.** Ten launchers live behind their own bespoke `*DialogDeps` interface inside the form module (`SchemaDdlForms.ts`, `SequenceDdlForms.ts`, `ViewFormDialog.ts`, `MaterializedViewFormDialog.ts`, `RelationDdlActions.ts` — nine near-identical `execute`/`onSuccess`/`onError` re-declarations with copy-pasted JSDoc); thirteen others expose only a form class and let `SqlAdminController` open-code `openSqlPreviewDialog({...})` itself. From the controller side, this shows up as `execute: sql => executeDdl(this._connectionId, sql)` repeated 26 times, `onError: msg => this.notifyError(new Error(msg), ref)` 22 times, and the schema-fetch preamble duplicated three times across `SqlAdminController.ts`. `createView` and `createMaterializedView` (`SqlAdminController.ts:1278-1324`) are byte-for-byte identical apart from which dialog opener and preview function they call. One generic `DdlDialogDeps<TSpec>` plus a controller-side `ddlDialogDefaults(ref)` would collapse this and pick one convention — a design call, see below.

### Backend — operations

**16. `graph.py` duplicates all four of `table_structure.py`'s queries and result-shaping blocks.** Indexes, constraints, and foreign-key queries plus their shaping are each written twice, differing only in scope predicate (`graph.py:213-380` vs `table_structure.py:47-307`); a *third* copy of the same 4-join index query exists as `IndexDetailQuery` (`table_structure.py:111-123`). `graph.py` already imports two shared constants from its sibling — the shaping is half-shared, half-copied. See Priority 1 #12 for the drift this has already produced.

**17. `SchemaColumnsQuery` duplicates `ListColumnsQuery`'s entire query — including a two-arm `pg_depend` sub-select its sibling flags as "the easiest thing here to get wrong" — and the copy has already lost fields.** `graph.py:119-146` vs `list_columns.py:78-115`: same UNION ALL, re-typed with different aliases, but missing the `att`/`format_type` join, so `graph.py`'s `ColumnMeta` always has an empty `fullType` and null `defaultExpr` despite its own docstring (`graph.py:168-169`) claiming the same contract shape. Harmless today only because the one frontend consumer doesn't read those fields.

**18. `_require()` is copy-pasted verbatim into four DDL preview modules, and `sql/ddl.py`'s `_require_ident` re-validates the same values a fifth way.** `ddl_table.py:24-43`, `ddl_view.py:26-45`, `ddl_schema_sequence.py:22-41`, `ddl_function_type.py:25-44` are identical bodies and docstrings; `sql/ddl.py:859-876` is the same rule applied redundantly on top for schema/sequence/function/type builders (13+ call sites) while the table/view builders validate nothing at that layer. One shared helper (in `operations/ddl.py` or `common.py`) replaces all five.

**19. The `get_result() called before apply()` guard is hand-written 33 times across 25 modules.** `base.py` declares the three-phase Query/Command contract but supplies no enforcement, so all 9 `list_*` handlers plus 16 others each re-implement the identical guard and the identical `_conn`/`_raw` field pair. A `CatalogQuery` base with a `_rows()` accessor, a default `apply()`, and the guard built in would let most of these handlers shrink to `_SQL` + a result comprehension. The test suite mirrors this exactly — 24 near-identical `test_get_result_before_apply_raises` functions.

**20. 22-24 route handlers in `main.py` are byte-identical apart from the op class — corroborated by two reviewers.** Every DDL-preview route body is `op = OP(c, body); await op.apply(); return op.get_result()` (24 occurrences, `main.py:962-1529`), and four smaller groups repeat three other one-shape bodies. Since every op class is already aggregated in `operations/__init__.py:80-148`, a `{slug: OpClass}` mapping plus one registration loop would replace ~590 lines of `main.py` with ~40 — and is the direct reason `main.py` is 1,616 lines, the largest file in the backend.

**21. Eight DROP-statement builders in `sql/ddl.py` duplicate the same clause assembly and have already drifted.** `cascade_clause`/`exists_clause` construction is repeated 10× and 6× respectively; the eight statement-level `drop_*` functions are the same three lines over a different keyword/target. The drift: `drop_view`/`drop_materialized_view` are the only two with no `if_exists` parameter at all, and `drop_routine` takes `cascade`/`if_exists` positionally where all five siblings make them keyword-only. `add_primary_key`/`add_unique` (`:400-459`) are likewise the same function twice.

**22. Two mechanisms map an error to an HTTP status, and the taxonomy's own class is bypassed.** `_domain_error_handler` maps the documented `DomainError` taxonomy (`errors.py`) to a response; `_pg_error_handler` (`main.py:177-185`) separately hardcodes statuses for driver errors, including the 409 that `errors.ConflictError` already exists for — making that class dead (Priority 3).

## Items likely needing a design decision

- **`SqlAdminController.ts`'s size (3,610 lines, 5+ unrelated responsibilities).** Panel-opening, DDL-dialog launching, navigator/roles-tree reveal, the query workspace + saved-query/history stores, address-bar resolution, export routing, and error/status plumbing all live in one class-first controller with no test coverage. `navigator/objectMenu.ts:31-42` already has to `Pick` 35 methods off it to describe what a context menu needs — external evidence the surface is doing too many jobs. A split by object kind (relations / routines+types / schema+sequence+index / roles / queries) plus a `controllerText.ts` for the pure helpers is the natural cut, but is a real design call, not mechanical.
- **The two competing DDL-launcher wiring conventions** (Priority 2 #5): per-kind wrapper module with a bespoke `*DialogDeps` vs. controller-inlined `openSqlPreviewDialog`. Nothing in the codebase currently distinguishes when to use which; converging on one is a design choice, not just deduplication.
- **DDL preview-op naming has drifted across four phases** (`operations/__init__.py:121-147`): `Preview`-prefixed, `Preview`-suffixed verb-first, and `Preview`-suffixed noun-first are all in use for the same concept. Picking one convention and renaming is worth doing deliberately rather than piecemeal.
- **`main.py`'s route-table shape** (Priority 2 #20): collapsing ~40 hand-written routes into a declared `{slug: OpClass}` table would also remove the registration-order hazard behind Priority 1 #15 — but changes how routes are declared and discovered, worth a short design pass rather than a mechanical find-replace.
- **Boolean env-var parsing** (Priority 1 #13): whether `ALLOW_USER_PRESETS` should route through the same `parse_bool`/`on`/`off`-aware parser as the other two flags, or whether the two parsers reflect a real semantic difference worth keeping — either way the current silent divergence and the README's wrong guidance should not both stand.

---

## Recommendation

The same treatment the library's audit got likely fits here too, scaled to this app's smaller size: batch Priority 1 (real bugs — several are live today, two verified against a running database, several corroborated independently by more than one reviewer) into a tests-first fix pass, since a number of the root causes (the four duplicated DDL forms, the diagram-panel family, the `list_*`/`graph.py` backend split) are also Priority 2 items — fixing the duplication and the bug together is cheaper than fixing the bug four times. Priority 2/3/4 can follow as a second pass, or fold into the same batch; the design-decision items above should be resolved (or explicitly deferred) before any of Priority 2's DDL-launcher or controller-split work starts, since several mechanical fixes depend on which convention wins.
